Rendered by two surfaces from this one file: the standalone page (/sentinel/blocklist) and the Admin Console pane Settings -> Sentinel -> Border blocklist. `sn_inline` is the only difference, and every form posts `return_to` so a control pressed inside the Admin Console comes back to it. What this page is NOT: a firewall. SATOM has no FortiGate client and no credential that could write one. This is a list; the operator pre-creates the deny policy that reads it. Same rule that already governs FortiWeb -- Sentinel never binds its own enforcement point during an incident. The one property this path gives up, said out loud on the page rather than only in the docs: block_ip on FortiWeb uses action=block-period, so THE APPLIANCE expires it and that expiry survives Sentinel being dead. A feed has none. The list is therefore rendered from the database on every fetch (so a stopped publisher cannot serve an expired entry), but a border that cannot REACH us keeps its last copy and those entries freeze. #} {% set sn_inline = sn_inline | default(false) %} {% set rt = 'pane' if sn_inline else 'page' %}

Border blocklist

The list SATOM publishes for a border firewall to read, and the point where an address is released from it. Every entry expires; nothing here is ever written to a FortiGate by this product.

“Expire & push” does not make the feed current — the feed is rendered from the database on every fetch and filtered by expiry, so there is no cached file in the serving path that could go stale. That button writes the audit copy.
