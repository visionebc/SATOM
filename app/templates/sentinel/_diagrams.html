2 · Flow diagrams
2.1 · Reference architecture — what talks to what

Two paths leave the collectors. The upper one is deterministic and always runs; the lower one is the model, and everything it produces lands in a field named ai_*. The only component holding credentials that can change an appliance is the response runner, and it is a separate systemd unit — not the web worker, and not the sweep.

2.2 · Processing — one attack-log row to one proposal

Each stage takes what the one before it produced and adds exactly one kind of fact. The two dashed taps are reads of the metrics store: an incident's evidence is not what the log said, it is what the log said compared against what this hour of this weekday normally looks like.

2.3 · Decision — every gate, in the order the engine applies them

Generated from actions.GATE_ORDER, which is the same tuple the test suite asserts a full pass through evaluate() emits. Any gate that refuses returns a reason, and the reason is what the console prints: “Sentinel did nothing” is not an acceptable state for this page to be in.

The chain is re-run at execution time, not only at approval. An action approved at 12:00 and executed at 12:03 is executed under 12:03's state: a kill switch thrown in between, a trust entry added, a maintenance window opened — each is somebody deciding “not this”.

2.4 · Autonomous response, verification and rollback

Applied is not effective. A rule that is present on the appliance and changes nothing is the case that has to escalate, and it is invisible to a check that only confirms the write succeeded.
