Why the model is not in the deciding path. This system's safety argument is that the number gating a change to a production firewall can be reproduced, line by line, during the post-mortem that follows the one time it was wrong. A component whose output is sampled from a distribution cannot be. So the model reads finished incidents and writes prose; it never detects, never scores, never executes.

What survives an AI outage: detection, correlation, scoring, evidence, gating and history. What is lost: the narrative. That asymmetry is the whole design.

{# ── baseline ───────────────────────────────────────────────────────────── #}
3 · Behavioural baseline — median and MAD, per hour of week

A security baseline is trained on data that contains attacks. With mean + standard deviation, one flood raises the centre and inflates the spread, so the next identical flood scores as less anomalous — the detector desensitises itself with every incident it sees. The median is unmoved by a minority of extreme samples and the MAD inherits that.

168 buckets, one per hour of the week: 8,000 req/s at Tuesday noon may be a sale; the same figure at Sunday 03:00 is not. It also keeps the output arguable — “17× the Tuesday-12h median” is a sentence someone can dispute, which is the point.

Buckets below the sample floor stay learning and never fire. An immature baseline that fires is a false-positive generator wearing statistics as a costume. Currently usable: {{ health.baseline.usable }}/{{ health.baseline.total }} ({{ health.baseline.pct_usable }}%).

Why the negatives matter most

Most scoring designs only add. The subtractions are what make this number usable: a thousand attacks the appliance blocked is a WAF doing its job, an exploit aimed at software the backend does not run is noise, and an authorised scanner produces a byte-identical log to an intruder. Only context separates the last pair, so context outweighs any single positive factor.

{# ── http + vuln ────────────────────────────────────────────────────────── #}
5 · HTTP outcomes and vulnerability intelligence

An HTTP status is not a vulnerability, and nothing here pretends otherwise. A 500 is a symptom that may come from an RCE, from a backend saturated by volume, or from an ordinary bug. What the status carries is the outcome of each attack request, and the two outcomes are opposites: a 403 from the appliance means the defence worked; a 200 on a request carrying an attack signature means it did not. A design that only counts attack events treats those two identically.

PatternReading
401 / 403 burst from one sourceauthentication attack — brute force or credential stuffing
many 404s over many URIsenumeration; reconnaissance rather than exploitation
403 dominant, from the WAFlowers the score — the attacker is being stopped
2xx on an attack-signature requestraises it sharply — evasion suspected
5xx surge behind the policybackend impact: an RCE crashing a worker, or exhaustion

Vulnerability intelligence is enrichment, not detection. It is keyed on the signature — and first on the CVE the device itself attached to the entry (signature_cve_id), which is the vendor's own statement about its own signature and better evidence than any local mapping table. The local table is the fallback for entries that carry none.

EPSS and CISA KEV outrank CVSS. CVSS scores how bad a vulnerability would be if exploited; EPSS estimates whether it will be, and KEV records that it already has been. A 9.8 nobody exploits is a worse use of an on-call night than a 7.5 with a Metasploit module. And the mirror is local: a per-incident lookup would hand a third party a real-time map of this fleet's attack surface as a side effect of defending it. Gate order, and why it is this order
  1. Global kill switch — one setting disables everything, everywhere.
  2. Protected network — checked before anything about confidence, so that a correlation bug concluding our own monitoring host is an attacker is structurally unable to act on it.
  3. Trusted source / maintenance window — authorised activity.
  4. Policy exists, is enabled, and its level permits acting.
  5. Score meets that action's own floor.
  6. Reversibility and TTL — every blocking action must expire on its own.
  7. Circuit breaker — a fleet-wide hourly ceiling, so a correlation bug during a flood exhausts a budget rather than a firewall.
  8. Mechanism verified — proved on a real device.

Each gate returns a reason, and the reasons are shown on the incident. “Sentinel did nothing” is not an acceptable console state; “did nothing because the source is inside 10.0.0.0/8” is.

7 · The AI wall

8 · False positives are a first-class outcome

false_positive is a terminal state of its own, not a flavour of closed. Closing a real incident and dismissing a false one are different facts about the detector, and folding them together destroys the only signal available for tuning it. The reason is mandatory, because a dismissal without a cause is a silent vote to keep generating the same alert forever.

Bringing a new installation up
  1. Map each appliance to its VM and hypervisor node under Context — until then the VM and host layers report unknown.
  2. Let collection run for at least the sample floor before trusting behavioural factors; the console shows how many buckets are usable.
  3. Register your scanners and monitors as trusted sources, with expiry dates.
  4. Populate the CVE mirror — sync if outbound is permitted, otherwise by hand.
  5. Leave the response engine disarmed until the incident stream has been reviewed by a human for long enough to trust it, and until at least one action transport has been verified on a real device.
