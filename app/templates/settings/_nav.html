This file is the single source: the console (settings/index.html) and every standalone Settings page (settings/sentinel.html) include it, so an entry added, renamed, re-icon'd or re-grouped here changes on all of them at once. Copying the markup into a page instead is how the horizontal strip that preceded this menu ended up with two entries pointing at one pane -- and nothing fails when two copies disagree: the operator simply gets a different menu depending on which URL they arrived by. Contract (all optional, all defaulted): nav_mode 'panes' -- entries switch a tab in THIS page (the console) 'links' -- entries navigate back to the console (a standalone Settings page, where the panes do not exist and a tab button would be a control that does nothing) nav_active the tab target ('tab-sentinel') or endpoint ('sentinel.docs') the caller is currently showing; it is drawn selected and its group is the one the server renders expanded is_admin whether admin-only groups are offered at all The tab TARGET is the identity of a section: the panes, the in-page links (#tab-auth), the URL-hash restore and tests/test_theme.py all key off it. Targets are therefore literal and NEVER translated -- only `label` goes through the translation call. (An identifier is not copy -- safeguards §68.) An item with `ep` instead of `t` is a link to a PAGE and is drawn with the leaving arrow. No entry uses it today: Sentinel's Architecture, Incidents console, Context and Response policy all became PANES at the operator's request, so all five of its entries stay inside the console. The branch is kept because the arrow is the only thing that distinguishes a row which replaces the whole page from one which does not, and the next entry that leaves must carry it. Sentinel is a group of its own -- a pipeline with its own incidents console and architecture, not one knob under Monitoring -- and it sits LAST at the operator's request, below Monitoring & Alerts.
