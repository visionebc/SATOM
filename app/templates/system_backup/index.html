How this works — backup architecture & runbook
The three copies
CopyWhatHow it gets thereRPO
1. This node (primary) Postgres (live) · bundles data/system_backups/ · device vault data/backups/ · JSON tree reports/ Created here (manual bundles, device backups, device sync)—
2. Standby / backup server Postgres (streaming replica) · full data/ copy (bundles + vault) Postgres streaming replication (continuous) + fm-ha-datasync.timer rsync every 5 min (standby pulls; inert on the primary and in standalone mode) ≈ seconds (DB) / ≤ 5 min (files)
3. Git (Gitea) Per-device JSON reports/<device>/_config.json — versioned, human-diffable Auto-publish hourly via fm-git-publish.timer (primary only) + on backup creation (default-on checkbox) + the manual button ≤ 1 h (or on demand)

Git holds only the JSON source of truth (text, diffable). Binary artifacts — pg_dump bundles and raw device-config exports — deliberately stay OUT of git and travel via rsync to the standby: git is the wrong tool for binary blobs.

Rollback / restore procedures
  1. Whole instance — pick a bundle above → Restore (type RESTORE). Takes a safety dump first, then pg_restore --clean + replaces reports/. If this node is dead, the same bundles exist on the backup server under /opt/fortinet-manager/data/system_backups/.
  2. One device's JSON to an older version — find the commit in Versions in git, verify with Compare, then in Settings → Git run: git checkout <commit> -- reports/<device>/ and publish. This rolls back the JSON snapshot only — it does NOT push config to the device (use Templates/Provisioning for that).
  3. Single appliance config — use the per-appliance Backups page (vault); device-level restore is currently dry-run gated pending a live canary round-trip.
  4. Total loss of both nodes — clone the repo from Gitea (reports tree = last published state), restore the newest bundle from any surviving copy (downloaded bundle or backup-server disk).
Failover notes
  • After a promote, fm-ha-datasync on the new primary becomes a no-op automatically (role guard) and fm-git-publish activates there (same guard, inverted) — no unit reconfiguration needed.
  • Gitea (192.0.2.53) and the standby live on the same Proxmox host (hypervisor03): if hypervisor03 dies, copies 2 and 3 are both offline until it returns — copy 1 (primary, hypervisor06) remains. Bundles downloaded via the button above are the operator-held fourth copy.
  • This page probes the peer over HTTP (/healthz/backups) — no SSH between nodes is required to verify the off-box copy.
