How this works — backup architecture & runbook
The copies (per artifact)
CopyWhatHow it gets thereRPO
1. This node (primary) Postgres (live) · bundles data/system_backups/ · device vault data/backups/ · JSON tree data/reports/ · versioned SoT store data/sot/ Created here (manual bundles, device backups, device sync)—
2. Standby / backup server Postgres (streaming replica) · full data/ copy (bundles + vault + reports + SoT store) Postgres streaming replication (continuous) + satom-ha-datasync.timer rsync every 5 min (standby pulls; inert on the primary and in standalone mode) ≈ seconds (DB) / ≤ 5 min (files)
3. Versioned SoT store (local + off-box) Content-addressed snapshots of every device's config (data/sot/objects/, gzip, deduplicated — an unchanged config costs zero bytes per cycle) with the version index in Postgres. Replaced the git-committed reports/ history on 2026-08-05: a repo receiving the whole fleet hourly grows without bound at scale, and this store keeps working with Gitea down Hourly sync (device_sync, id5) records a version on every config CHANGE; nightly device_inspect (id12, 02:45) uploads new blobs to backup-server /system/sot/; plus the manual button ≤ 1 h (or on demand)
4. External backup server (backup-server) App-pushed DB bundle (/system/ — this app's pg_dump, off-rack) · device-pushed config backups (/configs/<device>/) · firmware .out binaries (/firmware/) The nightly system_backup (id11) pushes the pg_dump bundle to /system/ over SFTP (default on). Separately, the appliances push their OWN config backups (config system backup → SFTP, e.g. fw6 daily 02:00) — zero dependency on this app or either HA node DB: ≤ 24 h · per-device schedule (fw6: ≤ 24 h)

Git now holds only the application CODE. Device-config history, pg_dump bundles and raw device-config exports all live under data/: they travel via rsync to the standby, and the pg_dump bundle + SoT blobs are additionally pushed to backup-server /system/ so they have an off-rack copy on a separate failure domain. No backup copy depends on an external service being up.

The device-pushed backups on the external server are browsable here: External backup server card → Browse — compare two pushes (A → B), search inside B, click a filename (or View B) to read the extracted config text inline, or download the raw archive. Firmware .out images listed there are pulled into Infrastructure → Firmware, sha256-verified.

Rollback / restore procedures
  1. Whole instance — pick a bundle above → Restore (type RESTORE). Takes a safety dump first, then pg_restore --clean + replaces reports/. If this node is dead, the same bundles exist on the backup server under /opt/satom/data/system_backups/.
  2. One device's JSON to an older version — pick the two versions in Device config versions, verify with Compare. The store keeps every recorded version under data/sot/objects/ (gzip JSON, named by sha256) — extract with zcat to inspect or re-import. This rolls back the JSON snapshot only — it does NOT push config to the device (use Templates/Provisioning for that).
  3. Single appliance config — use the per-appliance Backups page (vault); device-level restore is currently dry-run gated pending a live canary round-trip.
  4. Total loss of both nodes — reinstall from Gitea or an installer bundle (code), then restore the newest DB bundle from any surviving copy (downloaded bundle, backup-server /system/, or the device-pushed backups on the external backup server). The bundle carries data/reports/ AND the SoT store, so version history survives too.
  5. Application code to an older version — Application code card above → pick the commit → Queue rollback. Goes through the self-update runner (checkout + pip + migrate + restart). Roll the standby the same way afterwards. Note: newer DB schema is not auto-downgraded — pair a code rollback with a database bundle restore when a migration was involved.
  6. Firmware — the .out images live on the external backup server (/firmware/), inventoried in the firmware SoT repo (manifest). Pull brings the image into Infrastructure → Firmware (sha256-verified) and the per-appliance Upgrade / Downgrade action flashes it from the console. A device factory-reset recovery = flash firmware + restore its own pushed config backup from /configs/<device>/.
Failover notes
  • After a promote, satom-ha-datasync on the new primary becomes a no-op automatically (role guard) — no unit reconfiguration needed. (The hourly satom-git-publish that used to activate here was retired on 2026-08-05 with the git SoT; the source of truth is now data/sot/, which the datasync already carries.)
  • Check that your copies are not all on one hypervisor. The three automatic copies — this node, the standby via satom-ha-datasync, and the external backup server — are only three copies if they fail independently. Two nodes and a backup host that share a hypervisor are one copy wearing three hats, and nothing in this page can detect that: SATOM sees three reachable destinations either way. Verify it where the guests actually live, not here. Bundles downloaded via the button above are the operator-held copy that is definitionally elsewhere.
  • A bundle alone does not recover a total loss: FERNET_KEY is not in it, deliberately. Run satom diagnose recovery to check somebody holds it.
  • This page probes the peer over HTTP (/healthz/backups) — no SSH between nodes is required to verify the off-box copy.
