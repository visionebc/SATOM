# Git backup and surviving a Gitea outage

The repo carries two different assets: the **application code** and, under
`reports/`, the **per-device source of truth** (a diffable `_config.json` per
appliance, refreshed hourly). Gitea (`git.example.net`, LXC 237 on hypervisor03) is a
*distribution* point for both — not a custody point. This document is about what
happens when it is not there, and about the artifact that makes that survivable.

## What breaks when Gitea is down

Nothing in the request path. Only two commands in the whole codebase talk to the
remote: `self_update.py` (`git fetch`) and `git_service.git_publish` (`git push`).
Everything else — the UI, device management, `device_sync`, pg_dump bundles, the
appliance pushes to backup-server, the HA rsync — is unaffected.

| Function | Effect while the remote is unreachable |
|---|---|
| Software Update & HA | `git fetch` fails → no code update **and no code rollback** |
| `satom-git-publish.timer` (hourly) | commits `reports/` locally, push fails; the timer still exits 0 |
| Firmware SoT manifest | unreadable (the `.out` binaries live on backup-server, so pulls still work) |
| Reconciler (AUTO) | cannot fetch → drift is not reconciled |
| Sync Prod | blocked — the dev repo is the source |
| `requirements.txt` bump after a pip change | the pin is not persisted; the next code update reverts the library |

**No data is lost during the outage.** The commits pile up locally and push
themselves when the remote returns.

## The dangerous part is the return, not the outage

`deploy/self_update_runner.py` rewrites the checkout with:

```
git reset --hard origin/<branch>
```

Any commit that exists here and not on the remote becomes unreachable and is
eventually garbage-collected. With the reconciler in **AUTO** (its default), that
can fire on its own the moment Gitea comes back and reports `behind > 0`.

The `reports/` *files* would be regenerated by the next `device_sync` (≤1 h), so
current state returns. What would be gone for good is the **history** of those
days — which is the entire reason the git copy exists (the A→B diff viewer,
`git checkout <sha> -- reports/<device>/`).

### The guard

Before the reset the runner now calls `preserve_local_commits()`:

* local commits not on the target → `refs/backup/pre-reset-<UTC stamp>`
* a dirty worktree → `git stash create` (builds a commit object without touching
  the index or worktree) → `refs/backup/pre-reset-<stamp>-dirty`

Refs are never pruned, so `git log refs/backup/pre-reset-…` recovers everything.
**If the commits cannot be parked, the update aborts** — a deferred update beats
silent history loss. A failure to stash a dirty tree is reported but not fatal:
`reports/` is dirty in normal operation and regenerates on the next sync.

The System Backup page lists any `refs/backup/*` that exist.

### The alert

`ahead > 0, behind == 0` — the exact signature of a failing push — used to fire
nothing: `git.diverged` requires `behind > 0` and `git.behind` requires
`behind > 25`. The new **`git.ahead_unpushed`** keys off *age*, not count (one
commit stuck for three days is worse than twenty in the last hour):

* warning once the oldest unpushed commit passes `alerts.git_ahead_max_hours`
  (default 6 h, Settings → Alerts → "Git unpushed max")
* critical at 8× that threshold

## The artifact: `git bundle`

`app/services/git_backup.py` writes a **git bundle** — one file holding the whole
history and every ref (`--all`, which includes the `refs/backup/*` safety refs).
It is verifiable offline (`git bundle verify`) and clonable directly. No server,
no daemon, no credentials embedded.

Delta-compressed it is a few MB (the 208 MB `.git` on disk is mostly unreachable
objects and old packs), so retention is cheap — default 7 per node.

### Where the copies land

| Copy | Location | How it gets there |
|---|---|---|
| this node | `data/git-bundles/` | the button / the `git_bundle` automation |
| standby | same path | `satom-ha-datasync` mirrors `data/` every 5 min |
| off-rack | backup-server `<system_path>/git/` | SFTP push (default on) |
| operator | your laptop | the download button |

backup-server is a **separate failure domain on purpose**: Gitea and the standby both
live on hypervisor03, so a hypervisor03 outage takes copies 2 and 3 offline together. backup-server
is on hypervisor04, the primary on hypervisor06.

> `reports/` and `.git` are deliberately **not** in the HA rsync. The standby has
> its own git checkout; rsyncing `reports/` over it would leave its worktree dirty
> and break its own `reset --hard`. The bundle is the correct vehicle for that
> history, and it goes further off-box than the rsync does.

### Using it

```bash
# integrity, before trusting a copy
sha256sum satom-repo-<ts>.bundle       # compare with the value shown in the UI
git bundle verify satom-repo-<ts>.bundle

# total loss: rebuild from the bundle alone
git clone satom-repo-<ts>.bundle satom

# selective: pull the rescued history into an existing checkout
git fetch satom-repo-<ts>.bundle '+refs/*:refs/recovered/*'
git log refs/recovered/backup/pre-reset-<stamp>
```

### Operational notes

* Deletes are **primary-only**: `satom-ha-datasync` rsyncs `data/` with
  `--delete`, so a bundle deleted on the standby comes back within 5 min.
* Schedule it with the `git_bundle` action in Automation
  (`params.push_server` defaults to the saved setting).
* Take one **by hand before any update while the remote is unreachable** — that is
  precisely when the local commits exist nowhere else.
