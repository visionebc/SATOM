How a probe becomes a two-year chart

Monitoring is a time series, because the signal is a value changing — not its current reading.

1

Sweep

One scheduled action, every 3 minutes

2

Probe

Synthetic request, management API or read-only CLI

3

Grade

Thresholds, or drift against the previous fingerprint

4

Sample

Value, payload and status stored per probe

5

Roll up

min/avg/max per hour and per day, before pruning

⏱️

A probe interval is a multiple of the sweep

A probe only fires when its own interval has elapsed and a sweep tick happens, so a 5-minute probe under a 3-minute sweep is really a 6-minute probe. Intervals are constrained to multiples so the configured cadence is the real one.

🧮

Roll-ups run before pruning

The hourly bucket has to see the samples the retention cap is about to delete. Daily buckets are aggregated from hourly ones with a sample-weighted mean, so an hour with one reading does not weigh the same as an hour with twelve.

🔌

The sweep is not a scheduled extra

Roll-up happens inside the probe run rather than as its own scheduled action, because nothing in this product seeds schedules — a feature that depends on the operator creating a row does not exist on a fresh install.

Privilege

Who runs what

Three accounts, one root service, and a boundary that survives an update.

👤

Service account

Owns the application tree and runs the web worker, the scheduler, the reconciler and every timer. Login shell disabled. Its entire sudo grant is two commands: test the web-server configuration, and reload it.

🔑

Privileged runner

The only root service. The web worker queues a request file; the runner performs updates, curated dependency changes, unit installation and restarts — then verifies health and rolls back on failure. If a second root unit ever appears, the boundary has been reintroduced.

🧑‍🔧

Installer & operator accounts

Separate from the service account and from each other, each with a narrowly-scoped sudo rule the tool itself prints — so a systems team can approve the rule without receiving the repository. The installer's grant is temporary; what keeps running afterwards is not root.

📌

Drop-in, never a hand-edited unit

Every update re-copies the shipped unit templates, so an edited unit silently reverts to running as root. The service account is pinned through a drop-in written by all three places that touch units — installer, migrator and update runner.

🔁

Read-only peer trust

The standby generates its own key pair and pulls; the private key never travels. Its public key is authorized on the primary pinned to the peer address and to a forced command that can only read the data directory — structurally incapable of writing.

🗃️

Node-local vs replicated state

The data tree replicates and is backed up; certificates, the virtualenv and the certificate-renewal journal are deliberately node-local — the node that fails to renew is exactly the node that could not record its own failure if the journal lived on the replica.

High availability & layered backups

Two-node active/standby clustering is built into the installer — not bolted on.

🔁

Primary / standby pair

PostgreSQL streaming replication with enforced TLS and mutual certificate authentication; application data rsynced to the standby every 5 minutes with role guards, so a promoted standby never overwrites the primary.

🔑

One-paste cluster join

The primary generates a single join key at install time; paste it on the secondary and replication, shared secrets and node certificates configure themselves. Each node mints its own leaf certificate locally.

🧯

Defense-in-depth backups

Live database, portable backup bundles, git-versioned device configs and an external SFTP backup server — four independent copies across failure domains, summarized in a live coverage matrix.

Trust & encryption in transit

Every internal channel is encrypted, and the app proves it with live probes — not assumptions.

🔏

Internal CA

The primary node operates a built-in certificate authority. Node certificates are issued, renewed nightly, and rolled back automatically if an import breaks the web front.

🔒

Enforced database TLS

Replication and application connections run over TLS with mutual certificate verification — plain or cert-less connections are refused, and the policy (minimum protocol, ciphers) is tunable from the UI.

🛰️

Authenticated peer probes

Node-to-node health checks ride HTTPS and carry a shared identity key, so each node can trust — and render — the other's state without SSH access.

📡

Live encryption monitoring

A monitoring page shows one card per channel — app↔app, app↔DB, replication, git — with protocol, cipher, enforcement and authentication, each badge backed by a real probe.

🧾

Audited writes everywhere

Every write path lands in the audit log; risky operations go through Change Requests with maintenance-window approval gates.

🗝️

Secrets encrypted at rest

Appliance credentials and integration secrets are Fernet-encrypted in the database; API tokens are scoped, owner-capped and product-bound.
