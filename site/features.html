🔄 Manager ↔ device sync

The heart of the platform: a scheduled read path that keeps the database and git in lock-step with every live appliance, and a minimal-diff write path back to the device.

1

Schedule

Hourly sync + nightly deep inspect, targeted per product

2

Harvest

REST API per section, automatic SSH/CLI fallback

3

Normalize

One canonical snapshot shape for every device kind

4

Ingest

Written to the PostgreSQL device cache

5

Version

JSON tree per device committed & auto-published to git

  • DB-first reads. The UI reads from the local cache, so browsing a fleet is instant; a refresh-live escape hatch re-queries the appliance on demand.
  • Discovery & deep capture. A discovery plan enumerates every section of a device and captures it into the normalized cache — the same plan drives FortiWeb, FortiADC and FortiAnalyzer.
  • Product-aware scheduling. The hourly device_sync and nightly device_inspect actions fan out across the whole fleet, filtered by device kind.
  • Minimal-diff writes. Saving an object pushes only changed fields back to the device, with a dry-run preview and a full audit entry on every write.
  • Drift detection. The harvested config is diffed against git — a drift view surfaces exactly what changed on the box since the last known-good snapshot.
🧭

Because the harvest, normalize, ingest and git-publish steps are shared across products, adding coverage for a new device line reuses the entire pipeline.

🗄️ The database

A PostgreSQL database is the single source of truth — for device configuration, the editable API map, users, audit and every operational record.

  • Device configuration cache — the normalized snapshot of every appliance, so reads never wait on the box.
  • Endpoint registry — the REST URI map lives in the database, not in code: when a firmware upgrade moves an endpoint, an operator repoints it from the UI.
  • Appliance inventory — connection details, product kind and per-device flags; credentials are Fernet-encrypted at rest.
  • Identity & governance — users, roles, API tokens, the audit log and Change Requests are all first-class tables.
  • Live schema tools — an ER diagram of the running schema and read-only introspection views, straight from the app.
  • Enforced TLS — application and replication connections require TLS with mutual certificate verification; cert-less connections are refused.

🛡️ Signatures

Full management of FortiWeb attack signatures and the exceptions that keep them from blocking legitimate traffic.

  • Signature browser — every signature set and rule, searchable across the cached configuration.
  • Per-signature exceptions — add, review and remove exceptions with the object in context.
  • Guided WAF exceptions — a lifecycle (detect → inject → review) with template locks, so exceptions are tracked rather than forgotten.
  • Fleet-wide view — signature posture across every FortiWeb, not one box at a time.

📐 Templates

Reusable, locked templates for policies and exceptions — apply a known-good shape across the fleet instead of hand-editing each device.

  • Policy & exception templates with locks, so a curated baseline can't be accidentally mutated.
  • Clone & migrate — copy a policy or object set across devices with reference resolution and a pre-flight checklist.
  • Lifecycle tracking — templates carry state (applied, drifted, superseded) rather than being fire-and-forget.
  • Naming conventions & taxonomy — rules, section catalogs and field datasheets keep applied objects consistent.

🧭 Web Protection & policies

The FortiWeb management surface, mirroring the appliance GUI with safety rails the console doesn't have.

  • Server Policy table mirroring the FortiWeb menu, with minimal-diff saves.
  • Guided policy clone / migrate across devices: dummy-VIP rules, reference resolution, pre-flight checklist.
  • Safe cascade delete with a full dependency preview before anything is removed.
  • Web Protection area mirroring the FortiWeb 7.6 menu — 166 curated object kinds.

🧩 Generic object editor

One spec-driven form engine edits any registry endpoint — the reason the platform covers ~500 endpoints without 500 bespoke screens.

  • Stacked slide-over panels, create-references-in-place, and a dry-run preview on every write.
  • ~500 registry endpoints editable through the single engine, driven by the database-backed spec.
  • Live API consoles per product with audited, permission-gated writes.
  • Fleet-wide object search across every device's cached configuration.

🌐 Multi-product workspaces

Global, FortiWeb, FortiADC and FortiAnalyzer workspaces with strict, per-browser-tab product scoping.

  • Per-tab product context — each browser tab keeps its own active administrative domain.
  • FortiADC — load-balancer objects, virtual servers, real-server pools, LB lookup, certificate deploy over REST.
  • FortiAnalyzer — full JSON-RPC integration speaking both API dialects, a live registry-bound menu, and Device Manager views.

📦 Device operations

The day-to-day appliance lifecycle, from discovery to firmware.

  • Discovery / rediscovery and deep capture into the normalized cache.
  • Config backups over REST with automatic SSH/CLI fallback, plus a restore vault.
  • Firmware upgrade runbooks and boot-partition management.
  • Built-in SSH console with read-only command presets.
  • Provisioning workflows, hardware inventory and capacity views.

🗂️ Source of truth & backups

Four independent copies across failure domains, summarized in a live coverage matrix.

  • Git source of truth — every appliance's config harvested into versioned JSON, refreshed hourly, auto-published.
  • System Backup & Restore — database bundles, device vault, one-click code rollback, embedded recovery runbook.
  • Backup coverage matrix — every stream with format, destinations, cadence and a live state badge.
  • External SFTP backup server with per-device browse / compare / search / download.
  • Firmware source of truth — manifest in git, binaries on the backup server, sha256-verified pulls.
  • Git drift view and reports history with an A→B diff viewer.

🔁 High availability

Two-node clustering is part of the installer, not bolted on.

  • Primary / standby with PostgreSQL streaming replication and a role-guarded 5-minute data sync.
  • Replication TLS-enforced with mutual certificate verification against an internal CA.
  • Git-driven reconciler keeps deployments converged with the repository.
  • Cluster status page; node-to-node HTTPS probes authenticated with a shared identity key.

🔐 Security & access

Defense in depth from login to write path.

  • Two-factor authentication, LDAP auth and granular role-based access control.
  • Audit log on every write path; Change Requests with maintenance-window approval gates.
  • Scoped API tokens (read ⊂ write ⊂ admin, owner-capped, product-bound).
  • Secrets encrypted at rest; nonce-based CSP; rate limiting; object locks.
  • Node TLS manager — import or issue from the internal CA, nightly auto-renew, auto-rollback on bad imports.
  • Encryption-in-transit monitoring — every badge backed by a live probe.
  • Per-workspace scoping is enforced server-side — a product workspace never renders the manager's own infrastructure, and the endpoints behind those cards answer 403 rather than merely being hidden.

🧱 Privilege model

The web application does not run as root, and the boundary is written down rather than assumed.

  • A dedicated service account owns the application tree and runs the web worker, the scheduler, the reconciler and every timer. Its login shell is disabled.
  • Exactly two sudo commands — validate the web-server configuration and reload it. That is everything the worker needs to activate a certificate. Package installation and unrestricted systemctl are refused on purpose: granting a package manager is granting root, because packages run their own maintainer scripts.
  • One privileged runner, and only one. Updates, dependency changes and unit installation are queued as a request file and executed by a separate root service — the web worker never escalates.
  • Drop-in enforcement. The service account is pinned through a systemd drop-in, not by editing the unit, because every update re-copies the shipped unit template. A hand-edited unit silently reverts; a drop-in does not.
  • Read-only trust between nodes. The standby generates its own key and pulls; the key is pinned to the peer address and to a forced command that can only read the data directory.
  • Three separate accounts — installer, service and operator — each with its own narrowly-scoped rule, printable from the tool itself so it can be handed to a systems team without shipping the repository.
🔎

The full model, including what was deliberately refused and why, is published in the privilege-model manual.

⏱️ Automation & self-update

The platform runs and maintains itself.

  • Scheduled actions catalog — config syncs, deep inspections, database bundles, repository bundles, certificate scans and monitor sweeps, each with per-product targeting.
  • Background jobs with pause / resume / stop, and a job manager that keeps the full history.
  • Work nobody is waiting for stays quiet. Recurring sweeps do not raise a progress window; only a sweep that fails reaches the notification area. A control the operator cannot act on is worse than no control at all.
  • Maintenance means maintenance. An appliance parked for maintenance is skipped by automatic runs — and a run whose entire target set was parked reports skipped, not failed, so it never accumulates a fake failure streak. A manual run still reaches it, because parking a device is usually the prelude to working on it.
  • Self-update from the UI via the privileged runner, with per-step logs, health verification and a code-rollback path.
  • Library manager — PyPI update checks plus per-package upgrade / rollback from a curated allowlist, with an import smoke test, a health check and automatic rollback on failure. There is no free-form package installation from the web interface.
  • Local commits are never destroyed by an update. Anything not yet on the remote is parked on a backup ref before the checkout is reset — and if it cannot be parked, the update aborts.

⌨️ Operator console

A local command-line tool for the node whose web interface is the thing that is broken — 96 commands across four verbs.

get

State

Health, version, paths, units, roles

show

Reference

Command tree, runbooks, manuals, sudoers

diagnose

Check

24 checks, one exit code

execute

Act

Repair, seed, back up, reinstall

  • It works when the application does not. Nothing in the console imports the web framework or the ORM at module level — a tool that needs a healthy virtualenv to tell you the virtualenv is broken is not a diagnostic tool.
  • It degrades by privilege instead of failing. Read verbs run as any user; state-changing verbs require root and refuse with the full command line, an explanation and a distinct exit code — never a traceback.
  • It runs from a root-owned copy outside the application tree, so a compromised web worker cannot rewrite what an administrator runs under sudo.
  • diagnose install separates infrastructure from protections — the check that catches a fresh node with every capability and no coverage.
  • diagnose code compares the newest source file against each running process, catching the sidecar that is still executing yesterday's code — a failure whose only symptom is that manual runs pass and scheduled ones fail.
  • diagnose python compiles every module and explicitly imports the ones the application only imports lazily, because a module nobody imports at collection time can be syntactically broken while the health check still answers 200.
  • Manuals without a network — show docs prints any manual straight to the terminal, which is what makes the published copy safe to be the only rendered one.
  • The command tree is data. A new command is one entry; the parser, the ? help, completion, the privilege gate and the JSON renderer all read that same structure — and the test suite fails if an entry omits its help text or its privilege class.
  • Decoration is for a terminal, content is not. Piped output carries no escape sequences and is never truncated; --json is never decorated; the output path cannot crash on an encoding it cannot represent.

📜 Certificates

A central certificate manager for the whole fleet — and for the platform's own service certificate.

  • Issuance via ACME or an internal enterprise CA. The ACME path ships a curated catalog of 30 DNS providers plus generic escape hatches, and the catalog is data: a new provider is a row, not a release.
  • Credentials reach the signer through the environment, never the command line. The signing process gets a minimal, hand-built environment — the application's own database URI and encryption key are not inherited — and every secret is redacted from the logs.
  • The account key persists. Registering a fresh account on every issuance burns the authority's rate limit and loses the ability to revoke what came before, so the account directory lives inside the replicated, backed-up data tree.
  • Lifecycle policy — revoke-on-supersede, expiry sweeps, SNI policies, and a fleet-wide inventory backed by live probes.
  • Service certificate management — import a PEM (key/certificate match validated, configuration tested, automatic rollback on a bad import) or issue from the internal CA with nightly auto-renewal.
  • A renewal journal, and a page for it. Every attempt is recorded as renewed / skipped / error with the error text, per node, and a failed renewal is its own alert — critical from three in a row. A nightly timer that only writes to the system journal is a failure nobody reads.
  • Private-key upload over SSH and REST deploy to the appliances.

📡 Monitoring & probes

Fleet health answers is the box alive? Metrics answers how much does it hold? Probes answer the question neither can: is the service still serving?

Deep monitors

The checks that reach into the appliance.

  • Service policy — a synthetic request to a published front end. One 200 proves interface, policy, proxy daemon and backend at once, and records latency and days of certificate left.
  • Interface — a name → address/state fingerprint per port. The drift against the previous sample is the event; an address change grades critical, and a watched port that disappears is named, never silently dropped from a shorter list.
  • Processor and memory — read from the appliance's own performance summary, understood in two different vendor wordings.
  • Proxy daemon — worker count, memory consumed and free, and the set of process IDs: a different PID is a silent restart, which no ordinary health check shows.

Service monitor

Telemetry read purely over the management API — no shell access.

  • Box sessions and connections per second.
  • Server-policy sessions, round-trip and application response time, plus per-member backend health.
  • HTTP throughput, graded on the peak of the window rather than the average.
  • HTTP transactions per bucket — and a zero here is cross-checked against live sessions before it is allowed to grade healthy.

History that outlives the samples

Raw samples are capped per probe; charts are not.

  • Hourly roll-ups kept 90 days, daily roll-ups kept two years — under 400 KB per probe.
  • min / average / max, not just the mean: a four-minute spike is invisible in an average and is exactly what the chart is opened for.
  • Transition counts per bucket survive the pruning of the raw samples — restarts and address changes stay visible long after the detail is gone.
  • The server picks the resolution and says which one it drew, because an hourly mean and a three-minute reading are not the same claim about the appliance.
  • Loading a page never touches an appliance. Every view is served from the database; probing happens in a background sweep or on an explicit button, so a monitoring page opens instantly and still opens when the device is powered off.
  • A health badge that can go red. Each appliance is graded on the worst of four signals — harvest, cache age, probes and capacity — and every non-healthy signal is printed on the card, so a state is never unexplained. unknown ranks below ok: a device nothing has been measured about is never rendered healthy, and a disabled probe is not a passing probe.
  • Discovery from the device — policies, a baseline set, one probe per interface, or the API telemetry set; ports are picked from a cached list, so the dialog opens with the appliance switched off.
  • Absence of data is never health — a disabled policy warns, an empty bucket list is an error, and a probe pointed at a port that no longer exists grades critical by name.
  • Every appliance workspace has its own monitoring, scoped by device kind, and never shows the manager's own infrastructure.

📈 Observability & analysis

See the fleet and the platform at once.

  • Fleet health — one card per appliance, graded on four independent signals, with every failing signal spelled out.
  • Metrics — inventory counts, audit activity and change history, scoped to the active workspace.
  • Infrastructure health (manager workspace only) — cluster peers, repository state, external backup server, database, systemd units and redundancy.
  • Encryption in transit — a card per channel: encrypted? which protocol and cipher? enforced? authenticated? — every badge backed by a live probe, never by configuration.
  • Traffic analysis and packet capture, straight from the appliance.
  • DNS & load-balancer lookup, log collection, flash reports and capacity planning.
  • Hardware inventory sweep over SSH, scoped to the appliances the current workspace can see.

🔔 Alerting

All of the above is only worth anything if silence means healthy. Thirteen signals, one engine, delivered by e-mail on a timer.

  • Certificates — inside the expiry window, unreadable, or a failed renewal attempt (critical from three consecutive).
  • Repository — unpushed commits older than the limit, a checkout too far behind, a diverged history, or a repository that cannot be read at all.
  • Backups — no bundle at all, none recent enough, or a check that itself failed.
  • Device health — the same four-signal ladder the page uses, plus a live network probe the page deliberately does not have. One device, one finding, with every failing signal as a line in the message: five mails about one dead appliance is noise, and filtered noise is a disabled alert.
  • Scheduled actions — a run failing repeatedly, and an enabled action that is simply overdue. Without the second signal a dead scheduler looks perfectly healthy, because it produces no failed runs to count.
  • The engine itself — the guard on the guard.
⚖️

Severity is part of the cooldown key. A device or an action that degrades from warning to critical inside the quiet period still reaches the operator — a fixed key would suppress precisely the escalation the alert exists for. And the severity in the mailbox is the same severity as on the page: if the two can disagree, the operator learns to trust neither.

🎨 Appearance

Logo, favicon and colours are operator-editable, without ever handing the operator a stylesheet.

  • 34 design tokens in ten groups — sidebar, top bar, surfaces, accent, brand ramps and glow, text, status, elevation, layout and typography.
  • The editable surface is the token list, not the stylesheet. Free-form CSS in a themed page is stored injection — one closing brace ends the rule and starts another — so every value is validated by kind, and gradients are parsed structurally rather than waved through by a character allowlist.
  • The token registry is generated from the stylesheet. A hand-written list is a copy, and the first release that adds a variable would silently leave the editor without that control; the test suite fails if the two drift.
  • A theme stores only what it changes, so a later improvement to the shipped look still reaches every theme that did not override it.
  • Contrast is audited, not assumed. Every text/background pair is scored against the accessibility ratio with alpha composition; below the legibility floor the save requires an explicit acknowledgement.
  • Three ways back from a bad choice — revert to the shipped look, activate a built-in, or run one command on the console. The built-ins cannot be edited or deleted, and deleting the active theme falls back rather than leaving the console unthemed.
  • Four built-in palettes ship (Aurora, Slate, Graphite and the original Classic), and the logo and favicon live in the replicated data tree so they survive a rebuild and reach the standby.
  • No dark console, and the page says why — around a hundred and forty status tints are still literal, so a dark canvas would leave islands of light. Published as a limit instead of insinuated.

📚 Documentation

Twenty-two manuals, one source, three surfaces — and a publication path that redacts and then refuses.

  • The repository is the only place a manual is edited. The published site and the console renderer both derive from those files; a test fails if they drift.
  • One rendered copy on the internet, not one per node. A second rendered copy running on a management server is how internal addresses got published once already.
  • Publishing redacts, then scans its own output and aborts — naming pattern, file and line. A warning inside a publication pipeline is a leak with a receipt.
  • Publication is opt-in: a document absent from the register is not published at all.
  • Manuals without a network. The operator console prints any manual to the terminal, which is what makes a single published copy safe for an isolated management network.
  • Content is never hidden by presentation. Section animation is progressive enhancement with three independent guards — because a scroll animation once left the longest manuals rendering at zero opacity while the HTML, the status code and the leak scan were all perfectly correct.

🚀 Deployment

From a blank host to a running HA pair, guided.

  • Interactive Linux installer — online on any major distribution family, or fully air-gapped offline bundles for Debian 12, RHEL 9 and openSUSE Leap 15. The two RPM bundles are deliberately not interchangeable and the wrong one is refused up front.
  • A preflight that runs before anything is touched — and reports every blocker at once instead of stopping at the first. It checks effective write access rather than just the user id, the init system, the package manager, base-image utilities, the interpreter version, disk, memory, ports, clock and outbound reachability, plus the cluster prerequisites when a cluster is chosen.
  • Standalone or 2-node cluster — the secondary joins with a single pasted key, generates its own trust material and mints its own certificate. Private keys never travel between nodes.
  • systemd units, a TLS front end, PKI bootstrap, the operator console and a sysadmin manual with three separate sudo policies.
  • Protections have to be armed. Schedules are database rows and operator edits outrank seeds, so a brand-new install has every capability and no coverage — one console command creates the recommended minimum set, and the install manual says so in its own section.
  • Over 1,800 automated unit and integration tests, including guard tests that are verified by mutation — the guard is reintroduced deliberately to confirm the test actually fails.
