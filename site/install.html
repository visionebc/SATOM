Installation

One interactive installer, two modes. It asks for IP, port, admin password and standalone / cluster — and handles everything else: packages, PostgreSQL, PKI, systemd, nginx TLS.

OnlineAny distro family

Connected install

Fetches OS packages and Python wheels as it goes. Detects apt, dnf/yum, zypper or pacman and maps package names per family; PostgreSQL paths are interrogated from the engine itself, so Debian, RHEL, SUSE and Arch layouts all work.

# step 0 — reports, changes nothing
./install-satom.sh --preflight
# then, as root on a fresh host
./install-satom.sh
  • Checks required packages, installs what's missing, warns on outdated versions
  • Requires systemd and Python ≥ 3.10 (installed automatically where the default is older, e.g. RHEL 9)
OfflineDebian 12RHEL 9openSUSE 15

Air-gapped install

Self-contained bundles per family — OS packages, Python wheels and the application — for hosts with no internet access. The installer auto-detects bundle/ and refuses a bundle built for the wrong family with a clear message.

# Debian 12
tar xzf satom-offline-<ver>-debian12-amd64.tar.gz
# RHEL / Rocky / AlmaLinux 9
tar xzf satom-offline-<ver>-rhel9-x86_64.tar.gz
# openSUSE Leap 15 / SLES 15
tar xzf satom-offline-<ver>-suse15-x86_64.tar.gz
cd satom-installer && ./install-satom.sh
  • Debian bundle: full .deb dependency closure + wheels
  • RHEL bundle: a local dnf repository (with metadata) + wheels for Python 3.11 — dnf resolves only what the host actually needs
  • openSUSE bundle: a local zypper repository in a directory of its own. Both RPM bundles exist and are deliberately not interchangeable — different package names and base libraries — so the wrong one is refused up front instead of failing halfway through
  • Every bundle carries the ACME client and the privilege-escalation and SSH packages — a host with no network cannot fetch them mid-install
  • A bundle is a snapshot of the product at build time and records its own version — what it ships armed is the version it contains

Standalone or two-node cluster

Cluster setup is part of the same installer run — no separate procedure.

1️⃣

Install the primary

Choose cluster → primary. At the end the installer prints a one-line join key that encodes everything the secondary needs.

2️⃣

Join the secondary

Run the same installer on the second host, choose cluster → secondary, and paste the key. Streaming replication, shared secrets and the data sync configure themselves.

3️⃣

Certificates mint locally

The secondary receives the internal CA through the join key and mints its own leaf certificate during installation — private keys never travel between nodes.

Finishing the install: arm the protections

The guards travel with the code. The coverage does not — and this is the most common way an installation ends up unprotected.

Required

Nothing is scheduled on your behalf

Schedules are database rows, seeds are insert-only and operator edits outrank them, so the product never invents recurring work against live appliances. A brand-new node therefore has no scheduled actions and no alert recipient: its signals are computed and delivered nowhere, its source of truth is never refreshed, and no backup is ever produced.

# show the gap, then close it
satom diagnose install
satom execute seed actions --yes
  • Prints the plan first; never touches a schedule that already exists
  • Set an alert recipient under Settings → Alerts — a computed signal with nowhere to go is not an alert
Recommended

Grant the operator account, not root

Day-to-day diagnosis and repair run through the console, which needs one entry in the sudo policy — a single binary at a fixed path, owned by root. The tool prints the rule itself, with no privilege required, so it can be handed to a systems team without shipping the repository.

# prints the rule; changes nothing
satom show sudoers <account>
# then verify the boundary is intact
satom diagnose privilege
  • The path must be fixed and the file root-owned — a writable path makes the rule equivalent to unrestricted root
  • The check fails if the console was granted to the service account, which would be the same mistake
